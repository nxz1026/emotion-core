## 2. 缺陷 1：HEAD 上有一个红测试（时间炸弹）

### 证据

```
$ PYTHONPATH=src .venv/bin/python -m pytest tests/oracle tests/unit -q -p no:cacheprovider
FAILED tests/unit/test_alert_webhook.py::TestPushPendingWebhook::test_items_trigger_push
1 failed, 2581 passed, 1 warning in 54.24s
```

```
tests/unit/test_alert_webhook.py:133: in test_items_trigger_push
    assert "第 1 天" in body            # 当日创建 → 第 1 天
E   AssertionError: assert '第 1 天' in
    '... [ERROR] daily: test error 1（第 3 天 / 创建于 2026-10-17）
         [WARN] pool: test warn 1（第 4 天 / 创建于 2026-10-16）\n'
```

### 根因

- `src/emotion_core/algorithms/alerts.py:126-136` 的 `_days_active()` 取**墙上时钟**：
  ```python
  today = datetime.now(timezone.utc).date()
  return max(1, (today - created_date).days + 1)
  ```
- 测试桩（`tests/unit/test_alert_webhook.py:110-114`）把 `created_at` 硬编码为 `2026-10-17` / `2026-10-16`，而断言写死「当日创建 → 第 1 天 / 昨日创建 → 第 2 天」。
- 于是测试只在**提交当天（2026-10-17）**成立。审计报告 §7 记录的正是当天实测「8 passed」——它是绿的，第二天起必然红。今天（2026-10-19）实测 `第 3 天 / 第 4 天`。

### 影响

- 任何「测试全绿」门禁从 10-18 起就是红的；审阅者看到红测试容易去改 `src`（而 `src` 行为是对的）。
- 这是个**系统性**毛病，不是一次性手误：同一文件在审计 §5 里已因 `fake_items` 缺 `created_at` 红过一次（`KeyError: 'created_at'`）。

### 修法（二选一，都是一行级）——✅ 已按 A 落地，见 §9.1

```python
# A: 测试侧反推期望值（推荐，零侵入 src）
from datetime import datetime, timezone
today = datetime.now(timezone.utc).date()
assert f"第 {(today - date(2026,10,17)).days + 1} 天" in body
# B: 把 today 变成可注入参数（alerts._days_active(created_at, today=None)），测试传死值
```

## 4. 缺陷 3：Rust 孪生对账缺口（14 个导出函数零绑定级引用）

### 现状

### 缺口清单（按 `lib.rs` 声明的 49 个 `#[pyfunction]` × 全仓 `rust.fn` / `_rust.fn` 绑定级引用统计）

**完全零引用（死导出，生产=tests=0）：** `fold_candidates`、`layer_row`、`matrix`

**无任何绑定级测试守护：** `compute_derived`、`c1_uniqueness`、`c2_exchange`、`c3_elimination`、`c4_min_days`、`c5_strength_diverge`、`passed_of`、`split_checklist`、`w1_crowding`、`fold_candidates`、`layer_row`、`matrix`、`sole_top`、`top_group`（共 14 个）——即 **`indicators.rs`、`entry.rs`、`promotion.rs`、`ladder.rs`、`state.rs` 五个模块整体没有 Rust 侧对账**。

> `entry.rs` / `promotion.rs` 的函数在 `tests/` 里出现的裸名分别有 25～36 次，但那些命中的是 Python 参考实现（`algorithms/entry.py` 等），不是 PyO3 绑定——只看裸名会误判为「已覆盖」。

### 一条排除项（核过，非缺陷）

按 `entry → promotion → ladder → indicators` 的优先级补 `tests/oracle/test_*_rust_vs_python.py`；`fold_candidates` / `layer_row` / `matrix` 三个死导出与审计 §3 的 Python 死模块一并处置（要么接线，要么连同 `#[pyfunction]` 一起删）。

## 6. REA 适用性结论（要不要继续用）

**对 emotion-core：不值得继续。** 理由：

1. **没有 Python 分析面**——本仓 99% 的缺陷面积在 Python，REA 结构上不可达。这一条无解。
2. **二进制面在本机残缺**——aarch64 的 `.so` 连布局都读不了，且无重反编译器；而源码本来就在仓里，反编译收益接近 0。
3. **前端面只剩 1/5**——看板交互逻辑在 4 处内联 `<script>` 里，REA 明确不分析；live 抓取只拿到一个 1506 B 脚本，产出 1 条 low-confidence 猜测。

若仍想让它产生价值，先决条件按性价比排序：
1. 把内联 `<script>` 抽成独立 `.js` 文件（这样 REA 的 JS 面才完整，且顺带改善可测性）；
2. 装 Ghidra（免费）→ 才能反编译 arm64 `.so`（收益仍低）；
3. Python 主体只能走常规静态/动态分析（本次就是用 ruff/pytest + 定点探针做的）。

**REA 唯一真正帮上忙的动作**是提供二进制身份（sha256 / 构建时间 / 架构 / `.dep-v0` 缺失），它正是缺陷 2 的入口——但这件事实质上用 `sha256sum` + `git log -1 -- <file>` 就能更便宜地完成。

## 7. 踩坑记录

1. `inspect-binary-layout` 的 provider `pwntools-elf` **只支持 Linux x64**；本机 aarch64 ⇒ 直接 `capability_unavailable`。
2. `inspect-with-objdump` **不认** `--operation`（报 `Unknown flag: --operation`）；文档列出的取值 `file_headers|section_headers|symbols|relocations|dwarf|disassemble|disassemble_all` 得用别的传参形式（未跑通）。
3. `list-browser-targets` 必须带 CDP endpoint 参数，否则 `VALIDATION_ERROR: path ["endpoint"]`。
4. `analyze-web-bundle` **不自己起浏览器**：得先用 `chromium --headless=new --no-sandbox --remote-debugging-port=9222 --user-data-dir=/tmp/chrome-rea <url>` 起 CDP，再 `list-browser-targets` 拿 `target_id`。
5. `analyze-javascript-application` **不解析 HTML 内联脚本**，只把它们记成 `unknown` 覆盖节点（`inline_script_count` + limitation 文本）——而本仓看板逻辑恰恰都在内联脚本里。
6. npx 在本机必须 `NPM_CONFIG_CACHE=/tmp/rea-npm`（`~/.npm` 写不进去）。
7. **我自己的第一版探针写错了涨停价**：把 `close == pre_close` 当成涨停，导致 Rust 与 Python 都返回 `0`，差点得出「无漂移」的相反结论。正确涨停价 = `pre_close × 1.1`（600825 主板 10%）。教训：两轨对账探针必须先确认判据本身成立。
8. 绑定级覆盖率统计**不能用裸函数名 grep**：`compute_derived` 裸名在 tests 里出现 17 次，但 `rust.compute_derived` 出现 **0** 次——前者全是 Python 参考实现。
