## 一、总体评估（先说结论）

这套文档的完成度在同类个人项目里属于很高的一档：

1. **决策规则极简且可执行**——「策略语义照 lkl / 工程实现照 asel」一条规则解决了 C1~C7 全部口径冲突，这是整个合并工程的地基，不要动。
2. **取证扎实**——几乎所有结论都有行数、行号、实测数据支撑（3.5M 行全史实测、172 个重放信号、661 天 market_stat），没有拍脑袋。
   （「172 个重放信号」为 2026-09-26 建议稿时点口径；截止 2026-09-30 生产库实测：`signal` 162 行、全部 `source='replay'`、`source='live'`=0，**172 是当时预估**，现状见 `docs/05` §P4。）
3. **「不做什么」比「做什么」写得更好**——不选 DAG、不做实时、不伪造日内精度、不删业务事实。这些负面清单是项目能收敛的关键。

## 二、十条建议（按优先级）

### S1 ★ 最高优先：重新确认 Rust 选型，或采用「双实现、Python 先行」

`docs/07` §9 的实测数据其实和 Rust 选型**存在张力**：

- 实测：纯 Python 全史判据+连板 **3.2s**，pandas **1.6s**，瓶颈在 DB 读取 **11.2s**；
- 文档自己也承认：「Rust 把计算从 3.2s 压到 0.2s，但端到端只快 3 秒」「Rust 的真正价值是**保护算法源码**，性能是附带的」。

「保护源码」是正当的商业理由，**但它的代价需要在文档里写实**：

| 代价 | 具体表现 | 缓解 |
|---|---|---|
| 对账测试翻倍 | 每个算法要验证 Python 参考实现 == Rust 实现 == lkl 历史，**三边对账** | 先写 Python 参考实现并对账 lkl（两边），再逐模块移植 Rust（Rust 对 Python oracle） |
| 调试链变长 | 状态机算错时，要分辨是 Rust 层错还是外壳数据装配错 | Rust 侧只收 POD 数组、不碰 DB（已定），**外加**：每次调用落一份输入快照（可选开关），出错可离线重放 |
| CI/部署复杂 | maturin/PyO3 编译链 | 预编译 `.so` 入库发布，或锁定 `cargo`/`maturin` 版本 |

**建议的落地顺序（对 `docs/10` 阶段 2/3 的微调）**：

```
阶段 2a：algorithms/ 用纯 Python 实现全部算法（参考实现，可裸跑）
         → 与 lkl 逐日对账（661 天 market_stat / 172 信号 / _streaks oracle）
阶段 2b：对账全绿后，再逐模块翻译成 Rust core/
         → Rust 对 Python 参考实现对账（同输入同输出）
```

> 本段「172 信号」为 2026-09-26 建议稿时点**预估**（历史快照）；2026-09-30 实测 `signal` 共 162 行
> （全部 `source='replay'`），对账基准以实测为准，见 `docs/05` §P4。

好处：**对账金字塔始终有一个「已知正确」的 Python 基准**。如果直接上 Rust，一旦对不上 lkl 历史，你无法区分是「翻译错了」还是「lkl 的 SQL 语义本身理解错了」。Python 参考实现同时也是最好的语义文档（接手者读 Python 比读 Rust 快）。

> 如果 ≤10 人的使用场景下「源码保护」不是硬需求，纯 Python 方案能让整个项目提前 2~3 个阶段交付。这个决策值得在开工前最后确认一次——但一旦定了就不要反复。

### S4 跨层数据结构需要单一事实来源（types 契约层）

`docs/11` 的模块清单里，Bar / DerivedBar / MarketStat / Signal / LadderDay 这些核心结构散在 `data/models.py`。建议：

```
src/emotion_core/domain/          # 或保留在 data/models.py，但按契约层对待
├── bar.py        # Bar, DerivedBar（判据输出）
├── market.py     # MarketStat, Phase, BuyWindow（状态机输出）
├── ladder.py     # LadderDay, LeaderIdentity
├── signal.py     # Signal, Checklist（c1~c5 + w1）
└── snapshot.py   # 展示层读取的视图模型（VM）
```

规则：
- **这些 dataclass 是全项目唯一的类型定义**，Rust 侧用同名同字段的 struct（serde 对齐字段名）；
- 展示层只读 `snapshot.py` 的视图模型，不直接拼裸 DB 行；
- 字段级标注口径：`volume: int  # 手（非股）` / `turnover_rate: float  # 百分数（非比值）` / `pre_close_cents: int  # 分`——单位写进类型注释，呼应 README 关键约束 1。

### S5 价格计算全程用「分」（int cents），消灭浮点

涨停价「错一分钱全错」（`docs/07` §2.1）。浮点 `round(x*1.1, 2)` 在边界值上有二进制表示误差风险。lkl 生产用的就是 SQL 整数式 `(round(pre_close*100)::bigint * 110 + 50)/100`——**这本质上就是分运算**。

建议：
- DB 存 `numeric`，进内存即转 `int`（分）；
- `utils/price.py` 与 `core/price.rs` 都只接受/返回**分**；
- 展示层最后一步才格式化成元。

这让「SQL 整数式 == Python 实现 == Rust 实现」的三边对账变成**整数相等判断**，没有 epsilon。

### S6 theme.py 的依赖注入需要一个明确的 Provider 协议

`docs/07` §4 已定「Wind 依赖改依赖注入」，建议落成具体协议（见 §4.4 data 层），并且：
- 日线链里 theme 数据缺失时 **降级不阻断**：`dragon_env` 的 G2/B4 条件记 `UNKNOWN`（奎爷「宁降档不猜」已有此语义），daily 链继续；
- Wind 配额账本（`ops_quota_ledger` 思想）并入 `data/sync` 的 provider 层统一打点。

### S7 编排层补一个「--from-step」断点续跑

线性链 + 全链中止（已定）有一个日常痛点：第 9 步 `theme` 挂了，修好后要重跑 1~8。建议 `daily.py` 支持：


### S8 展示层框架：维持标准库，但把路由收敛到一个登记表

`docs/09` 定「Python http.server 或轻量框架」。asel DD3 已拍板纯标准库，**尊重它**。但 lkl 的教训是 16 个路由里出了 4 个孤儿端点。建议：

### S9 config 版本化落地：config_hash 进每次运行

`docs/08` §3.3 已提「pipeline_state 加 git_sha / config_hash」。建议具体化：

## 三、跨层约定（动具体框架之前先定这些）

### 3.1 依赖方向（对 `docs/11` §5 的一处修订）

`docs/11` §5 写「data 依赖 algorithms」，§1 分层图又把 data 画在 algorithms 之上——两种画法会让 derive（数据层调用算法）的归属含糊。**建议明确为**：

```
utils          无依赖（纯工具）
domain         无依赖（纯类型）
core (Rust)    不依赖任何 Python
algorithms     依赖 core + domain + utils；不写 SQL、不直连 DB
data           依赖 domain + utils（SQL 全在这层）；不依赖 algorithms
services       ★ 新增薄层：编排数据装载（data）与计算（algorithms）的胶水
orchestration  依赖 services
presentation   依赖 data（只读）+ domain.snapshot；不调 algorithms 现算
llm            只被 services/presentation 可选调用；信号链路禁止 import（奎爷红线）
```

**关键新增**：`services/` 胶水层。原因：`docs/11` 说「algorithms 外壳不直接写 DB」，但 derive 的输出要写回 `derived_bar`——这个「取数→算→落库」的编排不属于算法也不属于 data，需要一个家。不放 services 层，这块逻辑就会流进 orchestration/daily.py，让线性脚本变肥。

### 3.2 错误与边界三原则（全项目统一）

| 原则 | 来源 | 落地 |
|---|---|---|
| 缺失不补零 | 奎爷 F6 | 分母 < `PROMOTION_MIN_DENOM` → `None`，不是 0 |
| 宁降档不猜 | 生态评级纪律 | 数据缺失条件 → `UNKNOWN`，评级取可用条件下的较差档 |
| 三态质量 | asel A4 | `status ∈ {limit_up, not_limit_up, unknown}`；「未知」≠「未涨停」 |

### 3.3 单位与价格纪律（README 关键约束 1 的代码化）

- `volume`：内存与 DB 统一为**手**；新浪源在 provider 边界 `/100` 归一（只许在这一处出现）；
- `turnover_rate`：**百分数**（5.23 表示 5.23%）；
- `pre_close`：**存列**，源端取（东财 f18），缺失用复权因子公式补算（`docs/04` §2.2 路径 B），**代码库全局禁止 `LAG(close)` 重算**（守护测试锁死）；
- 金额与价格：内部一律**分**（int），边界格式化。
