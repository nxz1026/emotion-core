## 二、十条建议（按优先级）

### S1 ★ 最高优先：重新确认 Rust 选型，或采用「双实现、Python 先行」

`docs/07` §9 的实测数据其实和 Rust 选型**存在张力**：

- 实测：纯 Python 全史判据+连板 **3.2s**，pandas **1.6s**，瓶颈在 DB 读取 **11.2s**；
- 文档自己也承认：「Rust 把计算从 3.2s 压到 0.2s，但端到端只快 3 秒」「Rust 的真正价值是**保护算法源码**，性能是附带的」。

「保护源码」是正当的商业理由，**但它的代价需要在文档里写实**：

| 代价 | 具体表现 | 缓解 |
|---|---|---|
| 对账测试翻倍 | 每个算法要验证 Python 参考实现 == Rust 实现 == lkl 历史，**三边对账** | 先写 Python 参考实现并对账 lkl（两边），再逐模块移植 Rust（Rust 对 Python oracle） |
| 调试链变长 | 状态机算错时，要分辨是 Rust 层错还是外壳数据装配错 | Rust 侧只收 POD 数组、不碰 DB（已定），**外加**：每次调用落一份输入快照（可选开关），出错可离线重放 |
| CI/部署复杂 | maturin/PyO3 编译链 | 预编译 `.so` 入库发布，或锁定 `cargo`/`maturin` 版本 |

**建议的落地顺序（对 `docs/10` 阶段 2/3 的微调）**：

```
阶段 2a：algorithms/ 用纯 Python 实现全部算法（参考实现，可裸跑）
         → 与 lkl 逐日对账（661 天 market_stat / 172 信号 / _streaks oracle）
阶段 2b：对账全绿后，再逐模块翻译成 Rust core/
         → Rust 对 Python 参考实现对账（同输入同输出）
```

> 本段「172 信号」为 2026-09-26 建议稿时点**预估**（历史快照）；2026-09-30 实测 `signal` 共 162 行
> （全部 `source='replay'`），对账基准以实测为准，见 `docs/05` §P4。

好处：**对账金字塔始终有一个「已知正确」的 Python 基准**。如果直接上 Rust，一旦对不上 lkl 历史，你无法区分是「翻译错了」还是「lkl 的 SQL 语义本身理解错了」。Python 参考实现同时也是最好的语义文档（接手者读 Python 比读 Rust 快）。

> 如果 ≤10 人的使用场景下「源码保护」不是硬需求，纯 Python 方案能让整个项目提前 2~3 个阶段交付。这个决策值得在开工前最后确认一次——但一旦定了就不要反复。

### S5 价格计算全程用「分」（int cents），消灭浮点

涨停价「错一分钱全错」（`docs/07` §2.1）。浮点 `round(x*1.1, 2)` 在边界值上有二进制表示误差风险。lkl 生产用的就是 SQL 整数式 `(round(pre_close*100)::bigint * 110 + 50)/100`——**这本质上就是分运算**。

建议：
- DB 存 `numeric`，进内存即转 `int`（分）；
- `utils/price.py` 与 `core/price.rs` 都只接受/返回**分**；
- 展示层最后一步才格式化成元。

这让「SQL 整数式 == Python 实现 == Rust 实现」的三边对账变成**整数相等判断**，没有 epsilon。

`docs/07` §4 已定「Wind 依赖改依赖注入」，建议落成具体协议（见 §4.4 data 层），并且：

## 三、跨层约定（动具体框架之前先定这些）

### 3.1 依赖方向（对 `docs/11` §5 的一处修订）

`docs/11` §5 写「data 依赖 algorithms」，§1 分层图又把 data 画在 algorithms 之上——两种画法会让 derive（数据层调用算法）的归属含糊。**建议明确为**：

```
utils          无依赖（纯工具）
domain         无依赖（纯类型）
core (Rust)    不依赖任何 Python
algorithms     依赖 core + domain + utils；不写 SQL、不直连 DB
data           依赖 domain + utils（SQL 全在这层）；不依赖 algorithms
services       ★ 新增薄层：编排数据装载（data）与计算（algorithms）的胶水
orchestration  依赖 services
presentation   依赖 data（只读）+ domain.snapshot；不调 algorithms 现算
llm            只被 services/presentation 可选调用；信号链路禁止 import（奎爷红线）
```

**关键新增**：`services/` 胶水层。原因：`docs/11` 说「algorithms 外壳不直接写 DB」，但 derive 的输出要写回 `derived_bar`——这个「取数→算→落库」的编排不属于算法也不属于 data，需要一个家。不放 services 层，这块逻辑就会流进 orchestration/daily.py，让线性脚本变肥。

### 3.2 错误与边界三原则（全项目统一）

| 原则 | 来源 | 落地 |
|---|---|---|
| 缺失不补零 | 奎爷 F6 | 分母 < `PROMOTION_MIN_DENOM` → `None`，不是 0 |
| 宁降档不猜 | 生态评级纪律 | 数据缺失条件 → `UNKNOWN`，评级取可用条件下的较差档 |
| 三态质量 | asel A4 | `status ∈ {limit_up, not_limit_up, unknown}`；「未知」≠「未涨停」 |

### 3.3 单位与价格纪律（README 关键约束 1 的代码化）

- `volume`：内存与 DB 统一为**手**；新浪源在 provider 边界 `/100` 归一（只许在这一处出现）；
- `turnover_rate`：**百分数**（5.23 表示 5.23%）；
- `pre_close`：**存列**，源端取（东财 f18），缺失用复权因子公式补算（`docs/04` §2.2 路径 B），**代码库全局禁止 `LAG(close)` 重算**（守护测试锁死）；
- 金额与价格：内部一律**分**（int），边界格式化。

**config.py**：

```python
"""全部阈值常量。策略口径值逐字照 lkl config.py，禁止顺手调参。"""
from __future__ import annotations
import hashlib, json
from dataclasses import dataclass, asdict
from datetime import date

@dataclass(frozen=True)
class Config:
    # ── 数据范围 ──────────────────────────────
    DATA_START: date = date(2024, 1, 1)        # 判定口径起点（数据层保留 2010 起）
    # ── 状态机（lkl emotion.py）────────────────
    CLIMAX_ZT: int = 80                        # 高潮：涨停家数 >
    ICE_ZT_MAX: int = 40                       # 冰点：涨停家数 < 且最高板 ≤ 3
    BOMB_RATE_FALLBACK: float = 0.42           # 自适应炸板阈值 fallback
    BOMB_RATE_WINDOW: int = 30                 # 前 30 交易日 median+σ
    # ── 龙头与信号（lkl entry.py / ladder.py）──
    MIN_LEADER_DAYS: int = 4                   # 唯一最高板门槛（可调 3，改了要记 ADR）
    SECONDARY_MIN_DAYS: int = 3                # 次级推荐放宽
    EXCHANGE_TURNOVER_MIN: float = 5.0         # c5 换手强度补偿（百分数）
    # ── 晋级率 ────────────────────────────────
    PROMOTION_MIN_DENOM: int = 3               # 分母不足 → None，不补零（F6）
    # ── 运维 ──────────────────────────────────
    MIN_COVERAGE: float = 0.90                 # 覆盖率硬门槛（asel A12）
    # ── 开关 ──────────────────────────────────
    SECONDARY_EXPORT_ENABLED: bool = False     # 次级推荐影子模式
    TRADE_EXPORT_ENABLED: bool = False         # 交易桥默认不导出
    LLM_PROFILE: str | None = None             # None=关；'agnes'=启用

CONFIG = Config()

def config_hash() -> str:
    """每次运行写入 pipeline_state / signal / eval_result（S9）。"""
    payload = json.dumps(asdict(CONFIG), default=str, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()[:12]
```

**price.py**（全项目唯一涨停价实现，守护测试锁定）：

```python
"""涨停价唯一实现。单位：分（int）。板块感知：主板10% / 创业30 科创68→20% / 北交所bj→30%。

口径来源：lkl utils/price.py:9（Decimal 参考）+ derive.py:48-52（SQL 整数式，生产用）。
两者语义等价；本实现用整数分运算，与 SQL 整数式逐分一致（S5）。
"""

def board_pct_milli(code: str) -> int:
    """返回涨跌幅的千分比（主板 100 = 10.0%）。"""
    if code.startswith("bj"):                 return 300   # 北交所 30%
    if code.startswith(("30", "68")):         return 200   # 创业/科创 20%
    return 100                                            # 主板 10%

def limit_up_price_cents(pre_close_cents: int, code: str) -> int:
    """涨停价（分）。四舍五入与 SQL (x*pct + 50)/100 一致。"""
    pct = board_pct_milli(code)
    return (pre_close_cents * (1000 + pct) + 5000) // 10000

def is_limit_up(close_cents: int, pre_close_cents: int, code: str) -> bool:
    return close_cents >= limit_up_price_cents(pre_close_cents, code)
```

```rust
#[pymodule]
fn emotion_core_rs(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(limit_up_prices, m)?)?;   // (pre_close_cents, codes) -> cents

    m.add_function(wrap_pyfunction!(build_ladder, m)?)?;       // derived(day) -> 梯队+龙头身份
    m.add_function(wrap_pyfunction!(check_entry, m)?)?;        // candidate + ctx -> c1..c5/w1 + pass
    m.add_function(wrap_pyfunction!(promotion_matrix, m)?)?;   // derived(d-1, d) -> 5层双口径
    m.add_function(wrap_pyfunction!(ecosystem_rating, m)?)?;   // 聚合输入 -> G/B 条件 + rating
    m.add_function(wrap_pyfunction!(detect_accelerate, m)?)?;  // A1/A2/A3
    Ok(())
}
```

**纪律**（照 `docs/07` §9.4）：
- 只收 POD（`i64` 分、`&[BarIn]`），不做任何 I/O；
- 连板实现要点（**最大风险点**，`docs/07` §2.2）：按 `(code, date)` 排序后**只遍历实际存在的行**，遇到非涨停行重置计数——停牌日无行，自然实现「停牌断档不打断」。**不按日历补齐**；
- 状态机：`_RULES` 优先级数组 `退潮 > 高潮 > 发酵 > 冰点`，首个命中定相；全未命中 → 继承昨日（`phase_inherited=true`），首日 seed 冰点；
- entry 的 c3 淘汰性：**集合相等判定**（`survivor_set == {candidate}`），精确保留；
- 单元测试在 Rust 侧用 `#[cfg(test)]`，每个模块至少一个 lkl 取证样例。

> S1 的「Python 先行」若被采纳，本层每个函数对应一个已通过 lkl 对账的 Python 参考实现，Rust 测试直接以 Python 输出为 oracle。
