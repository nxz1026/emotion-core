**设计**：`docs/10` §阶段 3 + `docs/11` §2.2

**阻塞项**：

| # | 问题 | 影响 | 解决 |
|---|---|---|---|
| 1 | `domain.Bar` ↔ `rust.Bar` 日期类型 | 所有函数 | `_to_rust_bar` / `_from_rust_bar` |
| 2 | `rust.DerivedBar` / `GroupStats` 无 `#[new]` | 无法从 Python 创建 | Rust 侧加 `#[new]` |

| 4 | `isinstance` 检查 | 测试期望 Rust 类型同时是 Python dataclass | `__class__` 欺骗 |

**切换策略**：解决阻塞后，每个模块 ~30 分钟（转换层 + 测试）。

### 顺带查出并修掉的真 bug（都不在原缺口清单里）

1. `derive` 全区间执行崩 `FeatureNotSupported: cannot convert NaN to bigint`——PG 的 numeric
   **NaN 大于一切非 NaN**，`pre_close > 0` 挡不住 NaN。库内 226 行新股首日 `pre_close=NaN`。
2. `stock_basic.first_bar_date` 全表 NULL（由 `sync` 步骤的 `refresh_first_bar()` 写入，

3. `CONFIG.NEW_ISSUER_FLOOR` 沿用 lkl 数据起点 `2023-11-26`，本库 daily_bar 首日为 `2024-01-02`
   → **2024-01-02~2024-03-29 共 58 个交易日「所有股票都算次新」、情绪计数全 0**。

### `sync` FAILED 的根因与处置（2026-09-27 追加）

**不是数据源滞后，是库内脏数据 + 派生日历自噬**：

- 交易日历由 `daily_bar` 的 distinct date 派生（`utils/dates.py`「交易日历是 data 的事实」）；
- 库内 `2026-09-27`（**周日**）有 5221 行，且 `open/high/low/close/amount` 与 `2026-09-24`
  逐行完全相同（5206/5206 匹配行全等，close 相同率 100%）——旧版 `snapshot_daily` 在
  V1 守卫内移之前，把实时快照盖上了传入日期（该守卫的 docstring 正是描述这个事故）；
- 于是日历把周日当成交易日 → `_trading_day_guard` 被骗过 → 目标日=周日 → sync 报
  「EM 最新数据日期 2026-09-24 ≠ 传入 2026-09-27」→ 链卡死在第一步，新 coverage/derive/emotion
  永远跑不到；
- 全库 664 个日期扫描「与前一日 close 相同率 >90%」：**只有 2026-09-27 这一处污染**。

处置：① 三张表删除该日数据（`daily_bar` 5221 / `derived_bar` 5221 / `market_stat` 1，
删前已 `\copy` 备份到 `/home/ubuntu/work/polluted-20260927-*.tsv`）→ 日历末交易日恢复为
`2026-09-24`，`derived_bar` 663 日 / `market_stat` 663 行；② `refresh_first_bar()` 重算 5218 行
首条日线日期；③ `_trading_day_guard` 增加**独立于库内数据**的工作日判据（周末直接跳过），
并补 4 条单测（含「日历被污染也拒绝周日」）。

**仍挡不住的**：节假日（工作日但休市，如 2026-09-25 中秋）——需要接独立日历源
