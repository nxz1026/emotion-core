# 08 · 编排层合并方案

- 日期：2026-09-26
- 状态：**方案稿，待确认**
- 起因：接手者说"确实是个伤脑筋的层"——两个仓库的编排范式**完全不同**
- 原则：**不要有复杂的编排**（接手者明确要求）

---

## 0. 一句话结论

**用"一个 Python 入口 + 线性步骤 + 表打点"**，不用 shell 脚本，不用声明式 DAG。
步骤顺序**照 lkl 的 `daily.sh`**（那是策略语义），状态管理**用 lkl 的 `pipeline_state`**（在用），
幂等**取 asel 的字节一致跳过**。

## 1. 两个仓库的编排范式对比

| 维度 | **lkl** | **asel** |
|---|---|---|
| 编排入口 | **shell 脚本** `daily.sh`（74 行） | **Python** `production_daily.py` |
| 步骤执行 | 12 步**线性 shell 命令** | 8 份快照 `for key in keys` 循环 |
| 输出方式 | **直接写 DB** + `reports/*.md` | **只读 DB** → 原子写**快照文件** |
| 状态管理 | **`pipeline_state` 表**（10 行，在用） | **JSONL 文件** `pipeline_state.jsonl` |
| 幂等 | `flock` 锁 + 交易日守卫 | **字节一致跳过**（`exists_same`） |
| 失败处理 | `set -euo pipefail` + `mark_failed` 入 alert | 记录后继续，不静默吞 |
| DAG | **无**（线性） | `StepRegistry`（声明式 DAG）但**生产未接线** |
| 覆盖率门槛 | 无 | `ASEL_MIN_COVERAGE_PCT`（拒绝装配半截数据） |
| systemd | **5 timer + 2 service** | **2 timer + 1 service** |
| 交易桥 | `trade export` + `trade_poll.sh 30` | 无 |

### 1.1 asel 的 StepRegistry 是"复杂编排"的代表

`asel/orchestration/steps.py` 定义了 `StepRegistry`（声明式 DAG），
但**生产入口 `production_daily.py` 根本不用它**——它用裸 `for key in keys:` 循环。
`pipeline.py` 只是 P0 **离线 demo**（不连 DB/不联网/不调 Wind）。

⇒ **StepRegistry 是未接线的过度设计**，合并时**不采用**。

### 1.2 lkl 的 daily.sh 步骤顺序（策略语义，必须保留）

```
守卫（EM 数据日期 == 目标日）
  ↓
1. fetch snapshot      全市场日线
2. fetch pool          东财三池
3. fetch hot           人气榜
4. fetch first-bar     次新剔除代理字段
5. derive              判据 + 连板
6. emotion             状态机（4 相）
7. ladder              梯队 + 龙头
8. signal              买入信号（5 条件）
9. promotion           晋级矩阵
10. theme              题材
11. dragon-env         生态评级（需 theme 之后）
12. review             日报（13 段）
13. outcome            结果回填
  ↓
14. trade export + trade_poll.sh 30   交易桥
15. health-push        健康推送
```

**依赖注释**（`daily.sh:6-8`，奎爷 v2.4）：
- `signal` 只需 `emotion` + `ladder`
- `promotion` 只需 `derived_bar`
- `dragon-env` 需 `market_stat` + `promotion_day` + `theme`（**故排在 theme 之后**）

                    └──────────────┬──────────────────────┘

**读法**：

⇒ **这不是 DAG 问题，是"线性 + 一处可并行"**。用**一个 Python 入口顺序执行**即可，不需要 StepRegistry。

## 3. 合并方案

### 3.1 编排入口：**一个 Python 脚本**

| 项 | 裁决 |
|---|---|
| 入口 | **一个 Python 脚本** `src/emotion_core/orchestration/daily.py` |
| 不用 | shell 脚本（lkl）、声明式 DAG（asel StepRegistry） |
| 风格 | **线性顺序执行**，每步打点，失败即停并告警 |

### 3.2 步骤顺序：**照 lkl daily.sh**（策略语义）

**不改动步骤顺序**——这是奎爷的依赖设计（`dragon-env` 必须在 `theme` 之后）。

### 3.3 状态管理：**用 lkl 的 `pipeline_state` 表**

| 表 | 行数 | 写入者 | 裁决 |
|---|---|---|---|
| `public.pipeline_state` | **10** | 有（`pipeline.py` 在用） | ✅ **采用** |
| `asel.ops_pipeline_state` | **0** | 无 | ❌ 不采用（空壳） |

**理由**：`pipeline_state` 在用、有写入者、有 RERUN 字典、有 mark_failed → alert 闭环。
`ops_pipeline_state` 是 0 行空壳，且 asel 生产实际用 JSONL 而非这张表。

**两表的基数差异**（子代理取证）：

| | lkl `pipeline_state` | asel `ops_pipeline_state` |
|---|---|---|
| 主键 | `step`（每步一行） | `(run_id, step_name)`（每 run 每步一行） |
| 基数 | **latest-state**（UPSERT 覆盖） | **append-only history**（每次运行都记） |
| 状态值 | RUNNING / OK / FAILED | pending / running / ok / failed / skipped |
| 额外字段 | for_date, exit_code, detail | rows_out, error, **git_sha, config_hash** |
| 生产写入 | ✅ 是（`_pipelined()` 包装器） | ❌ **否**（只有 docstring 对齐） |

**⇒ 采用 lkl 的 latest-state 语义**（更适合运维：一眼看到每步当前状态）。
**但保留 asel 的 provenance 思想**（`git_sha` / `config_hash`）——
在 `pipeline_state` 加两列，记录"这步是哪个代码版本/配置跑的"，便于追溯。

**保留 `asel.ops_pipeline_state` 表结构**（DDL 里的字段设计合理），但**不接线**——
状态走 `pipeline_state` 表。

### 3.4 幂等：**取两者所长**

| 机制 | 来源 | 用途 |
|---|---|---|
| **交易日守卫** | lkl（EM 数据日期 == 目标日） | 防周末/节假日陈旧行情入库 |
| **字节一致跳过** | asel（`exists_same`） | 快照文件不重复写 |
| **flock 重入锁** | lkl（`/tmp/lkl_daily.lock`） | 防 systemd 定时与人工手跑并发 |
| **覆盖率门槛** | asel（`ASEL_MIN_COVERAGE_PCT`） | 数据不足时拒绝装配 |

**合并后**：交易日守卫 + flock 锁 + 覆盖率门槛（针对数据装配）。

### 3.5 失败处理：**lkl 的全链中止 + mark_failed 闭环**

**两种哲学的差异**（子代理取证）：

| | lkl | asel |
|---|---|---|
| 失败策略 | **`set -euo pipefail` 全链中止** | per-snapshot `try/except` **继续** |
| 优点 | 安全（不产生半截数据） | 鲁棒（一个快照失败不影响其他） |
| 缺点 | 一步失败全链停 | 可能产生不一致的中间状态 |

**⇒ 采用 lkl 的全链中止**。理由：业务事实表之间有**依赖**（§2 步骤依赖图），
半截数据（如 derive 完成但 emotion 失败）比全链停更危险——下游会读到不完整的事实。

```python
try:
    step_xxx()
    mark_done("xxx")
except Exception as exc:
    mark_failed("xxx", str(exc))   # 入 pipeline_state + 入 alert
    raise                            # 不静默，让 systemd 记失败
```

**但保留 asel 的 `no_new_data` 检测**：如果今日数据与昨日字节一致（无新数据），
标记为 `skipped` 而非 `ok`——这能发现"上游数据停滞"（如回填挂了但没报错）。

### 3.6 输出：**写 DB + 可选快照**

| 输出 | 方式 | 理由 |
|---|---|---|
| 业务事实 | **写 DB**（lkl 方式） | 算法层直接落库，下游可读 |
| 快照文件 | **可选**（asel 方式） | 若展示层需要只读快照再加；**现在不强制** |

## 4. systemd 合并方案

### 4.1 现状：7 个 timer + 3 个 service

| 单元 | 时间 | 职责 | 归属 |
|---|---|---|---|
| `lkl-daily.timer` | 工作日 17:20 | 盘后全流程 | lkl |
| `lkl-health.timer` | 工作日 09:30 | 健康推送 | lkl |
| `lkl-close.timer` | 15:05 | 收盘对账 | lkl |
| `lkl-trade.timer` | 12:01 | 午间交易桥 | lkl |
| `lkl-dash.service` | 常驻 | 展示（8098） | lkl |
| `asel-backfill-daily.timer` | 16:00 + 17:00 | 行情回填 | asel |
| `asel-production-daily.timer` | 18:10 + 19:30 | 快照装配 | asel |
| `asel-dash.service` | 常驻 | 展示（8899） | asel |

### 4.2 合并后：**2 个 timer + 1 个 service**

| 新单元 | 时间 | 职责 | 合并来源 |
|---|---|---|---|
| `emotion-core-daily.timer` | 工作日 **17:20** | **全流程**：数据同步 → 计算 → 报告 → 推荐 | lkl-daily + asel-backfill + asel-production |
| ~~`emotion-core-close.timer`~~ | ~~15:05~~ | ~~收盘对账（交易桥）~~ | **2026-10-07 撤销**：该单元从未装到生产，且实际执行的是**完整 13 步 daily**，与 17:20 全量重复；「收盘对账」所需的 `orchestration/close.py` 从未存在。详见 README「systemd 仓/生产漂移」小节 |
| `emotion-core-dash.service` | 常驻 | 展示（单一端口） | lkl-dash + asel-dash |

**取消**：
- `lkl-health.timer`（09:30）→ 健康检查**并入 daily**（末尾一步）
- `lkl-trade.timer`（12:01）→ 交易桥**保留占位**，但不单独定时（P1 决策）
- `asel-backfill-daily` 的 17:00 重试 → 合并后由 daily 的**覆盖率门槛**兜底
- `asel-production-daily` 的 19:30 重试 → 同上

**为什么 17:20 一个入口就够**：
- asel 的 backfill（16:00，~1h）+ production（18:10）**合并成 daily 的一个"数据同步"步骤**
- 17:20 时 backfill 通常已完成（16:00 起跑，~1h）
- 若数据不足，**覆盖率门槛**拒绝装配并告警，人工补跑

### 4.3 交易桥的地位

**保留占位**（P1 决策）。`trade export` 作为 daily 的**最后一步**（可选，默认不导出到交易端）。
CPT 接入是**未来的事**（ADR 0001 D4）。

## 5. 合并后的日常流程

```
17:20  emotion-core-daily.timer 触发
  ↓
1. 交易日守卫（EM 数据日期 == 今天）
  ↓
2. 数据同步（东财主 + 新浪备）→ daily_bar
  ↓
3. 覆盖率门槛检查（不足则拒绝并告警）
  ↓
4. derive → emotion → ladder → [signal ∥ promotion] → theme → dragon-env
  ↓
5. review（日报）→ outcome（回填）
  ↓
6. 今日推荐（含打板价）→ 落库 + 展示
  ↓
7. 交易桥 export（可选，默认不导出）
  ↓
8. health-push（健康推送）
  ↓
打点：每步写入 pipeline_state（step/status/duration/exit_code）
```

## 6. 这个方案为什么"不复杂"

| 复杂方案（不采用） | 本方案（采用） |
|---|---|
| asel StepRegistry 声明式 DAG | **线性 Python 顺序执行** |
| asel 8 份快照文件 + 覆盖率门槛 | **写 DB**（快照可选） |
| lkl shell 脚本 + flock | **Python 入口 + 交易日守卫** |
| 7 个 systemd timer | **2 个 timer + 1 个 service** |
| 2 个 JSONL + 2 个状态表 | **1 个 pipeline_state 表** |

**核心**：**一个入口、线性执行、表打点、失败即停**。没有 DAG、没有声明式编排、没有多文件状态。

## 8. 历史数据清理（新增需求）

### 8.1 清理对象分类

| 类别 | 表/数据 | 当前行数 | 清理策略 |
|---|---|---|---|
| **可清理**（可再生/辅助） | `ingest_progress` | 5,554 | **归档或删除**（一次性写入，不再更新） |
| | `limit_pool_em` | 3,015 | **保留 30 天**（东财只覆盖近 30 交易日） |
| | `alert` | 8 | **保留 90 天**（已 ack 的告警） |
| | `llm_call_log` | 384 | **保留 1,000 条**（日志类） |
| | `eval_result` | 12 | **保留 50 条**（评估报告） |
| | 快照文件 | — | **保留 30 天** |
| **不清理**（业务事实/历史判定） | `daily_bar` | 3.5M | **不删**（原始行情，历史判定依赖） |
| | `derived_bar` | 3.3M | **不删**（判据，可重算但成本高） |
| | `market_stat` | 661 | **不删**（历史判定，策略语义） |
| | `ladder_day`/`promotion_day` | 8,656/3,305 | **不删**（历史判定） |
| | `signal`/`signal_outcome` | 6/6 | **不删**（信号历史） |
| | `position`/`trade_event` | 4/466 | **不删**（交易记录） |
| | `review_report` | 21 | **不删**（历史日报） |

### 8.2 核心约束（**绝对不可违反**）

1. **老库（lkl/asel）的行绝对不删** —— 那是唯一的对照基准。
2. **新库的业务事实不删** —— 历史判定依赖它，删了等于改历史数字。
3. **只清理可再生的辅助数据** —— 删除前记录删了什么（`data_revision`）。

### 8.3 自动清理

**并入 daily 的最后一步**（health-push 之后），每日执行：

```python
# 每日清理（幂等，可重复执行）
def daily_cleanup():
    # 1. limit_pool_em 保留 30 天
    db.execute("DELETE FROM limit_pool_em WHERE date < current_date - 30")
    # 2. alert 保留 90 天（已 ack 的）
    db.execute("DELETE FROM alert WHERE acked = true AND created_at < now() - interval '90 days'")
    # 3. llm_call_log 保留 1,000 条
    db.execute("DELETE FROM llm_call_log WHERE id NOT IN (SELECT id FROM llm_call_log ORDER BY id DESC LIMIT 1000)")
    # 4. eval_result 保留 50 条
    db.execute("DELETE FROM eval_result WHERE id NOT IN (SELECT id FROM eval_result ORDER BY id DESC LIMIT 50)")
    # 5. ingest_progress 归档（按月压缩）
    # 6. 快照文件保留 30 天
    # 7. 记录到 data_revision
    ...
```

**为什么并入 daily 而不是独立 timer**：
- 清理是轻量操作，不值得独立定时
- 并入 daily 保证"每天跑一次"，不会遗忘
- daily 有交易日守卫，非交易日不跑

### 8.4 手动清理（CLI 命令）

```bash
# 预览（dry-run，不实际删除）
emotion-core cleanup --dry-run

# 执行清理（默认保留策略）
emotion-core cleanup

# 指定保留天数
emotion-core cleanup --days 60

# 只清理某张表
emotion-core cleanup --table limit_pool_em

# 清理并归档（导出到文件后删除）
emotion-core cleanup --archive /path/to/archive/
```

**手动清理的输出**：
```
[清理] limit_pool_em: 删除 2,500 行（保留 30 天）
[清理] alert: 删除 3 行（已 ack，保留 90 天）
[清理] llm_call_log: 删除 0 行（当前 384 行 < 1000 上限）
[清理] eval_result: 删除 0 行（当前 12 行 < 50 上限）
[清理] ingest_progress: 归档 5,000 行到 ingest_progress_archive_20260926.csv
[记录] data_revision: 清理 5,503 行
```

### 8.5 清理与备份的关系

| 操作 | 时机 | 说明 |
|---|---|---|
| **清理** | 每日（自动） | 删辅助数据，保留业务事实 |
| **备份** | 每周（自动） | `pg_dump` 全库 |
| **归档** | 手动（可选） | 导出到文件后删除 |

**原则**：清理的是"删了也不影响系统运行"的数据。如果拿不准，**先归档再删除**。
