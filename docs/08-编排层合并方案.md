# 08 · 编排层合并方案

- 日期：2026-09-26
- 状态：**方案稿，待确认**
- 起因：接手者说"确实是个伤脑筋的层"——两个仓库的编排范式**完全不同**
- 原则：**不要有复杂的编排**（接手者明确要求）

---

## 0. 一句话结论

**用"一个 Python 入口 + 线性步骤 + 表打点"**，不用 shell 脚本，不用声明式 DAG。
步骤顺序**照 lkl 的 `daily.sh`**（那是策略语义），状态管理**用 lkl 的 `pipeline_state`**（在用），
幂等**取 asel 的字节一致跳过**。

---

## 1. 两个仓库的编排范式对比

| 维度 | **lkl** | **asel** |
|---|---|---|
| 编排入口 | **shell 脚本** `daily.sh`（74 行） | **Python** `production_daily.py` |
| 步骤执行 | 12 步**线性 shell 命令** | 8 份快照 `for key in keys` 循环 |
| 输出方式 | **直接写 DB** + `reports/*.md` | **只读 DB** → 原子写**快照文件** |
| 状态管理 | **`pipeline_state` 表**（10 行，在用） | **JSONL 文件** `pipeline_state.jsonl` |
| 幂等 | `flock` 锁 + 交易日守卫 | **字节一致跳过**（`exists_same`） |
| 失败处理 | `set -euo pipefail` + `mark_failed` 入 alert | 记录后继续，不静默吞 |
| DAG | **无**（线性） | `StepRegistry`（声明式 DAG）但**生产未接线** |
| 覆盖率门槛 | 无 | `ASEL_MIN_COVERAGE_PCT`（拒绝装配半截数据） |
| systemd | **5 timer + 2 service** | **2 timer + 1 service** |
| 交易桥 | `trade export` + `trade_poll.sh 30` | 无 |

### 1.1 asel 的 StepRegistry 是"复杂编排"的代表

`asel/orchestration/steps.py` 定义了 `StepRegistry`（声明式 DAG），
但**生产入口 `production_daily.py` 根本不用它**——它用裸 `for key in keys:` 循环。
`pipeline.py` 只是 P0 **离线 demo**（不连 DB/不联网/不调 Wind）。

⇒ **StepRegistry 是未接线的过度设计**，合并时**不采用**。

### 1.2 lkl 的 daily.sh 步骤顺序（策略语义，必须保留）

```
守卫（EM 数据日期 == 目标日）
  ↓
1. fetch snapshot      全市场日线
2. fetch pool          东财三池
3. fetch hot           人气榜
4. fetch first-bar     次新剔除代理字段
5. derive              判据 + 连板
6. emotion             状态机（4 相）
7. ladder              梯队 + 龙头
8. signal              买入信号（5 条件）
9. promotion           晋级矩阵
10. theme              题材
11. dragon-env         生态评级（需 theme 之后）
12. review             日报（13 段）
13. outcome            结果回填
  ↓
14. trade export + trade_poll.sh 30   交易桥
15. health-push        健康推送
```

**依赖注释**（`daily.sh:6-8`，奎爷 v2.4）：
- `signal` 只需 `emotion` + `ladder`
- `promotion` 只需 `derived_bar`
- `dragon-env` 需 `market_stat` + `promotion_day` + `theme`（**故排在 theme 之后**）

## 2. 步骤依赖图

```
                    ┌─────────────────────────────────────┐
                    │  fetch: snapshot / pool / hot /      │
                    │         first-bar                    │
                    └──────────────┬──────────────────────┘
                                   ↓
                              derive (derived_bar)
                                   ↓
                              emotion (market_stat)
                                   ↓
                              ladder (ladder_day)
                                   ↓
                         ┌─────────┴─────────┐
                         ↓                   ↓
                    signal (signal)     promotion (promotion_day)
                    [只需 emotion+ladder]  [只需 derived_bar]
                         ↓                   ↓
                         └─────────┬─────────┘
                                   ↓
                              theme (theme_tag/group)
                                   ↓
                           dragon-env (需 theme 之后)
                                   ↓
                              review (review_report)
                                   ↓
                              outcome (signal_outcome)
                                   ↓
                    trade export + poll → health-push
```

**读法**：
- **只有一处分支**：`signal` 和 `promotion` 都只依赖 `emotion`/`derived_bar`，**可并行**
- 其余**严格线性**
- `dragon-env` 必须在 `theme` 之后（依赖 theme_group/theme_tag）

⇒ **这不是 DAG 问题，是"线性 + 一处可并行"**。用**一个 Python 入口顺序执行**即可，不需要 StepRegistry。

## 3. 合并方案

### 3.1 编排入口：**一个 Python 脚本**

| 项 | 裁决 |
|---|---|
| 入口 | **一个 Python 脚本** `src/emotion_core/orchestration/daily.py` |
| 不用 | shell 脚本（lkl）、声明式 DAG（asel StepRegistry） |
| 风格 | **线性顺序执行**，每步打点，失败即停并告警 |

### 3.2 步骤顺序：**照 lkl daily.sh**（策略语义）

**不改动步骤顺序**——这是奎爷的依赖设计（`dragon-env` 必须在 `theme` 之后）。

### 3.3 状态管理：**用 lkl 的 `pipeline_state` 表**

| 表 | 行数 | 写入者 | 裁决 |
|---|---|---|---|
| `public.pipeline_state` | **10** | 有（`pipeline.py` 在用） | ✅ **采用** |
| `asel.ops_pipeline_state` | **0** | 无 | ❌ 不采用（空壳） |

**理由**：`pipeline_state` 在用、有写入者、有 RERUN 字典、有 mark_failed → alert 闭环。
`ops_pipeline_state` 是 0 行空壳，且 asel 生产实际用 JSONL 而非这张表。

**保留 `asel.ops_pipeline_state` 表结构**（DDL 里的字段设计合理），但**不接线**——
状态走 `pipeline_state` 表。

### 3.4 幂等：**取两者所长**

| 机制 | 来源 | 用途 |
|---|---|---|
| **交易日守卫** | lkl（EM 数据日期 == 目标日） | 防周末/节假日陈旧行情入库 |
| **字节一致跳过** | asel（`exists_same`） | 快照文件不重复写 |
| **flock 重入锁** | lkl（`/tmp/lkl_daily.lock`） | 防 systemd 定时与人工手跑并发 |
| **覆盖率门槛** | asel（`ASEL_MIN_COVERAGE_PCT`） | 数据不足时拒绝装配 |

**合并后**：交易日守卫 + flock 锁 + 覆盖率门槛（针对数据装配）。

### 3.5 失败处理：**lkl 的 mark_failed + alert 闭环**

```python
try:
    step_xxx()
    mark_done("xxx")
except Exception as exc:
    mark_failed("xxx", str(exc))   # 入 pipeline_state + 入 alert
    raise                            # 不静默，让 systemd 记失败
```

### 3.6 输出：**写 DB + 可选快照**

| 输出 | 方式 | 理由 |
|---|---|---|
| 业务事实 | **写 DB**（lkl 方式） | 算法层直接落库，下游可读 |
| 快照文件 | **可选**（asel 方式） | 若展示层需要只读快照再加；**现在不强制** |

## 4. systemd 合并方案

### 4.1 现状：7 个 timer + 3 个 service

| 单元 | 时间 | 职责 | 归属 |
|---|---|---|---|
| `lkl-daily.timer` | 工作日 17:20 | 盘后全流程 | lkl |
| `lkl-health.timer` | 工作日 09:30 | 健康推送 | lkl |
| `lkl-close.timer` | 15:05 | 收盘对账 | lkl |
| `lkl-trade.timer` | 12:01 | 午间交易桥 | lkl |
| `lkl-dash.service` | 常驻 | 展示（8098） | lkl |
| `asel-backfill-daily.timer` | 16:00 + 17:00 | 行情回填 | asel |
| `asel-production-daily.timer` | 18:10 + 19:30 | 快照装配 | asel |
| `asel-dash.service` | 常驻 | 展示（8899） | asel |

### 4.2 合并后：**2 个 timer + 1 个 service**

| 新单元 | 时间 | 职责 | 合并来源 |
|---|---|---|---|
| `emotion-core-daily.timer` | 工作日 **17:20** | **全流程**：数据同步 → 计算 → 报告 → 推荐 | lkl-daily + asel-backfill + asel-production |
| `emotion-core-close.timer` | 15:05 | 收盘对账（交易桥） | lkl-close |
| `emotion-core-dash.service` | 常驻 | 展示（单一端口） | lkl-dash + asel-dash |

**取消**：
- `lkl-health.timer`（09:30）→ 健康检查**并入 daily**（末尾一步）
- `lkl-trade.timer`（12:01）→ 交易桥**保留占位**，但不单独定时（P1 决策）
- `asel-backfill-daily` 的 17:00 重试 → 合并后由 daily 的**覆盖率门槛**兜底
- `asel-production-daily` 的 19:30 重试 → 同上

**为什么 17:20 一个入口就够**：
- asel 的 backfill（16:00，~1h）+ production（18:10）**合并成 daily 的一个"数据同步"步骤**
- 17:20 时 backfill 通常已完成（16:00 起跑，~1h）
- 若数据不足，**覆盖率门槛**拒绝装配并告警，人工补跑

### 4.3 交易桥的地位

**保留占位**（P1 决策）。`trade export` 作为 daily 的**最后一步**（可选，默认不导出到交易端）。
CPT 接入是**未来的事**（ADR 0001 D4）。

## 5. 合并后的日常流程

```
17:20  emotion-core-daily.timer 触发
  ↓
1. 交易日守卫（EM 数据日期 == 今天）
  ↓
2. 数据同步（东财主 + 新浪备）→ daily_bar
  ↓
3. 覆盖率门槛检查（不足则拒绝并告警）
  ↓
4. derive → emotion → ladder → [signal ∥ promotion] → theme → dragon-env
  ↓
5. review（日报）→ outcome（回填）
  ↓
6. 今日推荐（含打板价）→ 落库 + 展示
  ↓
7. 交易桥 export（可选，默认不导出）
  ↓
8. health-push（健康推送）
  ↓
打点：每步写入 pipeline_state（step/status/duration/exit_code）
```

---

## 6. 这个方案为什么"不复杂"

| 复杂方案（不采用） | 本方案（采用） |
|---|---|
| asel StepRegistry 声明式 DAG | **线性 Python 顺序执行** |
| asel 8 份快照文件 + 覆盖率门槛 | **写 DB**（快照可选） |
| lkl shell 脚本 + flock | **Python 入口 + 交易日守卫** |
| 7 个 systemd timer | **2 个 timer + 1 个 service** |
| 2 个 JSONL + 2 个状态表 | **1 个 pipeline_state 表** |

**核心**：**一个入口、线性执行、表打点、失败即停**。没有 DAG、没有声明式编排、没有多文件状态。
