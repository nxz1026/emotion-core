## 2. 停牌日阶梯保留「停牌（前 N 板）」

### 2.1 现状（为什么会整行消失）

链路：

```
daily_bar(停牌日 = loader 补的零成交顺延行，volume=0)
   └─ algorithms/indicators.py:59-73  compute_derived()
        suspended = b.volume == 0  → cont_days = 0（不计数、不打断链）
   └─ data/loader.py:107 load_ladder_candidates()
        WHERE d.cont_days >= 2  → 停牌行(0) 被过滤掉
   └─ algorithms/ladder.py:64 fold() → :137 persist() → ladder_day
   └─ algorithms/review/__init__.py:444 _sec_ladder()  → ②梯队全景
```

实测：`ladder_day` 里 600825 有 09-22~10-12 的行（cont 2..10）与 10-16 的行（11），
但 **10-14 / 10-15 完全没有行**；同日报告 ②段显示的最高组是「4板 慈文传媒(002343)」。
owner 要的是那两天能看到「600825 停牌（前 10 板）」。

### 2.2 设计约束（**别踩**）

- **不要改 `derived_bar.cont_days` 的语义**（不要让停牌日存 10）。它会连锁改变
  `algorithms/emotion.py:202 _top_amplitude()` → `:318 max_limit_days` → 阶段/`buy_window`/生态判定
  （`algorithms/state.py`、`algorithms/dragon_env.py`），且 Rust 孪生
  `src/emotion_core/core/src/state.rs:35` 也要同步；本机**没有 cargo**，改不动。
  这是「名义最高板」这个数字的口径，owner 已确认**数字不动**。
- 正确做法是**旁路**：停牌日额外产出一行「停牌行」，带**前一个有效身位**，标记为停牌，
  并且**不参与** `top_group / sole_top / max_limit_days` 的取值。

### 2.3 改动点

| 层 | 文件:行 | 改什么 |
|---|---|---|
| DDL | `data/schema.py:129` `ladder_day` | 加一列 `is_suspended boolean NOT NULL DEFAULT false` |
| 取数 | `data/loader.py:107 load_ladder_candidates()` | UNION 一组停牌行 |
| 领域 | `algorithms/ladder.py:64 fold()` | 透传 `is_suspended`；`top_group()`(:48) 排除停牌行 |
| 落库 | `data/loader.py` 的 `replace_ladder_day` | 写入新列 |
| 渲染 | `algorithms/review/__init__.py:444 _sec_ladder()` | 停牌行单独一行 |

### 2.4 规格

1. 停牌行定义：`daily_bar.date = D AND volume = 0 AND open = 0 AND close = 0`（与
   `data/bar_guard.py:84 is_padding_row()` 同一判据，**复用那个函数，别抄一遍**）。
   注意上游还有「close = pre_close > 0、volume = 0」的第二种顺延形状（见 `bar_guard.py:99-105`），
   本项只处理 OHLC 全 0 的那一种。
2. 身位：取该 code **在 D 之前最近一条 `cont_days > 0`** 的 `derived_bar.cont_days` 作为 `cont_days` 写进
   停牌行。SQL 建议用窗口函数一次算完，别逐票查：

   ```sql
   WITH susp AS (
       SELECT b.code, b.date
         FROM daily_bar b
        WHERE b.date = %s AND b.volume = 0 AND b.open = 0 AND b.close = 0
   )
   SELECT s.code, s.date,
          (SELECT d.cont_days FROM derived_bar d
            WHERE d.code = s.code AND d.date < s.date AND d.cont_days > 0
            ORDER BY d.date DESC LIMIT 1) AS prev_cont,
          true AS is_suspended
     FROM susp s
   ```

   只保留 `prev_cont >= 2` 且主板前缀（`CONFIG.BOARD_PREFIXES`）、非 ST、非次新的行——口径与
   `load_ladder_candidates()` 现有的 WHERE 子句一致。
3. `fold()`：停牌行的 `is_top = is_sole_top = false`，不参与 `top_group()` / `sole_top()`；
   `y_top_group_count / y_top_survivor_count` 照旧按「昨日最高组」算（停牌行不进组）。
4. 渲染（`_sec_ladder`）：停牌行**不并进板数分组**，在梯队末尾单独一行：

   ```
   - **10板（停牌）** [1只] 新华传媒(600825)
   ```
   以便与真实板数区分。
5. **数字口径不变**：`market_stat.max_limit_days / tradable_max_days` 一行代码都不改。

### 2.5 验收

- 重算 `algorithms/ladder.py:137 persist()`（脚本已有：`scripts/recompute_ladder_promotion.py --from 2026-10-13 --to 2026-10-16`），

  期望与改动前**完全一致**（4/4 与 5/5）。
- 报告 ②段出现「10板（停牌）…新华传媒(600825)」。

## 3. 策略对停牌/无行情标的一票否决

### 3.1 现状（真实事故）

`strategy_signal` 里 **2026-10-13 有一条 `600825 / expectation_repricing / BUY / score 92 / confidence 0.85`**，
理由「10连一字板确立极强预期…惯性冲高概率大」。但 600825 在 10-13、10-14、10-15 **连续停牌**：
新浪源实测 `SinaProvider.fetch_daily_bars("600825", 2026-10-09, 2026-10-16)` 只回 3 行
（10-09 / 10-12 / 10-16），`daily_bar` 里 10-13 无行、10-14/10-15 是零成交顺延行。

即：**策略对当日根本不能交易的标的照评不误，还给了 BUY。**

链路：

```
services/strategy/universe.py:43 build_universe()   ← watchlist + hot_rank(当日前 N)，无行情约束
   └─ services/strategy/runner.py:261 run_for_date() ← :281-286 取候选 → :298 与 skills 笛卡尔积
        └─ :147 _prompt() / :110 _parse()（action 合法性在 :115 附近）
   └─ :248 _item() → :336(主循环)/:381(补跑) items.append → :408 _signal_row → :429 _save_batch
```

（注意区分两套 signal：`domain/signal.py:9 Action` 只有 `BUY/SECONDARY/SELL/RECOMMEND`，
**没有 WATCH**；`WATCH` 只存在于 `strategy_signal` 这套 15 策略体系。见 §4。）

### 3.2 规格（两层，都要做）

**第一层 · 候选池**（`services/strategy/universe.py:43 build_universe`）：
候选必须**当日有真实成交**。在 `filter_codes()`（`:23`）之后加一道过滤：

```sql
SELECT code FROM daily_bar
 WHERE date = %s AND volume > 0
   AND left(code, 3) IN (...)      -- CONFIG.BOARD_PREFIXES
```

用 `IN`/`= ANY(%s)` 一次查，别按 code 循环查库。`--codes` 显式补跑路径
（`runner.py:281-286`：显式传 `codes` 时跳过 `build_universe`，只过 `filter_codes`）**也要过这道闸门**。

**第二层 · 硬闸门**（`services/strategy/runner.py`，两处 `items.append(_item(...))` ——
主循环 **:336**、补跑循环 **:381** —— 之前）：
即使 LLM 返回 `BUY`，只要该 `(trade_date, code)` 当日 `daily_bar.volume = 0` 或没有行，
一律降级——**推荐直接不写 `strategy_signal` 行**，改为写进 `skipped`，`reason="no_bar_today"`：

```python
# runner.py 里 _parse() 拿到 action 之后
if action in ("BUY", "WATCH") and not _has_tradable_bar(trade_date, code):
    skipped.append({"strategy": skill.name, "code": code,
                    "reason": "no_bar_today"})
    continue
```

`_has_tradable_bar()` 查 `SELECT 1 FROM daily_bar WHERE date=%s AND code=%s AND volume>0`，
**结果按日缓存**（一次查全市场当日可交易 code 集合）——现在一个交易日约 170 个 code × 15 策略，
逐次查库会退化。

**第三层（顺带核对）· 主信号链**：`algorithms/entry.check_signal()` 是否也可能对停牌股出 BUY？
请加一个断言式单测（构造某票当日无 bar 的场景，断言不产出 `Action.BUY`）；若已经防住，测试保留即可。

## 4. `WATCH` 信号推飞书 webhook

## 5. 通用纪律与门禁（四项都要过）

1. **架构分层**：`algorithms → services → data → domain`。algorithms 层不许直连 data 层，
   取数一律经 `services/`（现有例：`services/ladder_service.py`）。
2. **Rust 孪生**：`src/emotion_core/core/src/*.rs` 只在与 `algorithms/*.py` 同语义时必须同步；
   本机没有 cargo、`.so` 在部分测试里被 skip，**改不动就别改语义**（§2.2）。
3. **提交前门禁**（全绿才算完）：

   ```bash
   PYTHONPATH=src .venv/bin/python -m pytest tests -q -p no:randomly
   PYTHONPATH=src .venv/bin/python -m pytest tests/caliber tests/architecture -q
   ruff check . && ruff format --check .
   mypy src/emotion_core
   python scripts/check_doc_numbers.py
   python scripts/check_gate_coverage.py
   ```
