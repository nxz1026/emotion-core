## C0 为什么只剩这条

B 轮把「追强族」三种入场（封板价、开盘价、回踩价）和「妖股回调 / 炸板次日 / 龙头断板」

## C2 架构（三件套）

### ① 候选池扫描（盘中，不是盘后）

**修正**：C3 的结论是只做「首板 + 早盘封板」，而**首板在昨日梯队池里根本不存在**
（昨日 0 板 = 昨天没涨停）。所以池子不能由盘后产物预先给出，必须盘中从全市场扫：

- 扫描源：新浪 `Market_Center.getHQNodeData`（`node=hs_a`、`sort=changepercent&asc=0`、`num=100`），
  实测单请求即返涨幅榜顶部，含 `symbol/code/name/trade/changepercent/buy/sell/high/low/volume/ticktime`。
- 筛选：主板 7 前缀（`CONFIG.BOARD_PREFIXES`）、剔除 ST 与北交所、`changepercent >= 9.7`（10% 板）。
- 定板数：用上一次落库的 `derived_bar.cont_days`（T−1 日）判「首板」，**这是 ex-ante 字段**。
- 触发价：`limit_up_price_cents(pre_close_cents, code)`（T 日涨停价 = 今日 pre_close×板比，
  盘中可从五档的昨收字段得到），禁止 `*1.1`。
- 池子规模：涨幅 ≥9.7% 的主板票通常 5–40 只，单轮扫 1 请求 + 逐票五档 ≤ 40 请求。

### ② 盘中采集器（新，常驻）

- 交易时段（09:25–15:00）每 **30s** 一轮：
  1 次涨幅榜（上面那个接口）→ 命中票批量拉五档 `hq.sinajs.cn/list=...`（一次可带 30–50 只；
  新浪失败回退腾讯 `qt.gtimg.cn/q=...`）。
- 落新表 `intraday_quote(date, ts, code, price, bid1, bid1_vol, ask1, ask1_vol, chg_pct, at_limit)`，
  按 (date, code, ts) 主键；日增量 ≤ 40 只 × 660 轮 × 4 分钟粒度裁剪后约 1–2 万行。
- **不做**：不做 L2 撮合仿真（封单被扫无法模拟）、不做下单。

### ③ 触发 + 闭环

- 触发规则（初版，参数进模块常量，不进 `CONFIG.config_hash`）：
  `price >= 触发价` 且 `今日首封时刻 <= 10:00` 且 `昨日板数 == 0` 且
  `bid1_vol >= 阈值（初值 3 万手，需样本调）` 且连续 2 次采样成立 → 推「已封板」（附封单量）；
  随后若 `bid1_vol` 相对触发时衰减 > 70%，或价格 < 触发价 → 推「封单松动/破板」。
- 收盘回填：`derived_bar` 给出 `is_limit_up`（是否封到收盘）、`cont_days`；
  与 ADR 0002 同口径算 T+1/T+2 开盘收益，写 `trigger_outcome`。
- **定档门禁**：见 C4。在此之前产品面只说「已封板 + 封单 X 万手」，不给买卖指令。

## C3 已做的便宜实验：把「盘中打板」按真实成交口径算出来

探针 `_audit/probe_c_seal_quality.py`（只读，产物 `_audit/c_seal_quality.csv`）。
样本 = `limit_pool_em` 的 **ZT ∪ ZB** 两池（收盘封住 + 炸板，都有 `first_seal`），
2026-09-04~10-21 共 34 天，剔除一字板（`low == 涨停价`，封死后无对手盘）后 **n=1634 可成交**。
入场价 = T 日涨停价（`limit_up_price_cents`），卖点 = T+1 开盘（跌停封死顺延），费后双边 0.15%。

### 结论一：全样本仍然是负的，但结构是「双峰」

| 口径 | n | 每笔 | 胜率 |
|---|---|---|---|
| 全样本（涨停价买 → T+1 开盘卖） | 1634 | **−0.97%** | 39% |
| └ 封住到收盘 | 1146 (70.1%) | **+1.26%** | — |
| └ 炸板（持到 T+1 开） | 488 | −6.21% | — |
| └ 炸板（破板即当日卖，T 日收盘代理） | 488 | **−4.64%** | — |
| 组合（封住→T+1 开；破板→当日卖） | 1634 | −0.50% | — |

**盈亏平衡要求封住率 ≥ 78.6%，实际 70.1%** —— 差 ~9pp。这不是「没有 alpha」，
而是「alpha 全在封住的那一侧，而封住与否在买入时不可知」。C 的价值就是补这 9pp。

### 结论二：ex-ante 切片后，缺口收窄到 ~5pp

只有**买入时就能知道的字段**才能当过滤器。按昨日板数切（`derived_bar` 前一日 `cont_days`）：

| 片段（早盘 ≤10:00 首封） | n | 封住率 | 封住时 | 破板时 | 组合 | 盈亏平衡所需封住率 |
|---|---|---|---|---|---|---|
| 首板（昨日 0 板） | 567 | 65.6% | +1.89% | −4.71% | **−0.38%** | 71% |
| 二板（昨日 1 板） | 164 | 65.9% | +2.22% | −7.50% | −1.10% | 77% |
| 三板+（昨日 ≥2 板） | 100 | 69.0% | +1.35% | −8.52% | −1.71% | 86% |

⇒ **C 应只做「首板 + 早盘封板」**：离盈亏平衡只差 5.4pp 封住率。
封单量只要能把这 65.6% 抬到 71% 以上，这条线就是正的。

### 结论三：封板质量确有分辨力（但那是另一个视角）

按 `first_seal` 分档的**隔夜溢价**（T 收 → T+1 开，需 T 日收盘已持有）：
≤09:30 n=249 **+4.24%**/胜率 70%；09:30–10:00 +1.79%；10:00–11:00 +1.37%；
11:00–13:00 +0.69%；13:00–14:30 +0.75%；>14:30 n=35 **−1.15%**/20%。
按炸板次数：0 次 +2.43%、1 次 +1.86%、2 次 +1.22%、3+ 次 +0.34%。
⇒ 早封、不炸板的票隔夜溢价最强，**但这是「T 日收盘已持有」的视角，盘后无法执行**——
正是 C 要争取的那部分。

### 教训（第三次踩同一个坑）

`is_limit_up`（A 轮）、`is_exchange`（B 轮）、`cont_days`（本轮）都是**收盘后才知道的字段**，
拿它们当成交判据或分层维度，相当于偷看答案。
`cont_days` 尤其隐蔽：炸板股 `cont_days=0`，按它 groupby 会把所有炸板样本**静默归入 0 板组**
（pandas `groupby` 丢 NaN，东财 ZB 池该列全空），于是「1板 +1.90%、2板 +2.16%」全部是幸存者偏差。
ex-ante 可用的只有：昨日板数、首次封板时刻、封单量、开盘涨跌幅。

## D2 表 DDL

```sql
CREATE TABLE IF NOT EXISTS intraday_quote (
    date        date        NOT NULL,
    ts          time        NOT NULL,          -- 采样时刻（精度到秒，入库前截到分钟）
    code        text        NOT NULL,          -- 6 位纯代码
    name        text,                          -- 票名（判 ST 要用）
    price       numeric(12,2),                 -- 最新价
    prev_close  numeric(12,2),                 -- 前收（算涨停价要用）
    chg_pct     numeric(8,2),
    bid1        numeric(12,2),
    bid1_vol    bigint,                        -- 股（新浪单位），展示时 /100 成手
    ask1        numeric(12,2),
    ask1_vol    bigint,
    at_limit    boolean     NOT NULL DEFAULT false,
    src         text        NOT NULL,          -- 'sina' | 'tencent'
    PRIMARY KEY (date, code, ts)
);
CREATE INDEX IF NOT EXISTS idx_intraday_quote_code_date ON intraday_quote (code, date);

CREATE TABLE IF NOT EXISTS trigger_log (
    date           date     NOT NULL,
    code           text     NOT NULL,
    name           text,
    first_seal_ts  time,                       -- 首次触及涨停时刻
    trigger_price  numeric(12,2),              -- 涨停价（分算法算出）
    seal_bid1_vol  bigint,                     -- 触发时买一量（股）
    broke          boolean,                    -- 当天是否破板（收盘回填）
    broke_ts       time,                       -- 首次跌离涨停价的采样时刻
    closed_sealed  boolean,                    -- 是否封到收盘（derived_bar.is_limit_up）
    prev_days      integer,                    -- 昨日连板数（ex-ante，0=首板）
    entry_px       numeric(12,2),              -- = trigger_price（口径：触及即成交）
    exit_px        numeric(12,2),              -- T+1 开盘（跌停封死顺延 T+2）
    rolled         boolean,
    ret_pct        numeric(8,3),               -- 费后
    settled_at     timestamp,
    PRIMARY KEY (date, code)
);
```

> 采样削峰：同一分钟内同价同量不重复写（`ts` 截到分钟后 PK 冲突即跳过），
> 否则 40 只 × 660 轮会灌出无意义重复行。

## D4 主循环（`--loop`）

**R93 之后改口径**：原始采集归 CPT（`cpt-intraday-collect.timer` 每 2 分钟一轮，落
`public.intraday_seal_snapshot` 9 列），本仓**不再自己采**（§E2），主循环变成「读一轮 → 判触发 → 写台账」：

```
每 SCAN_INTERVAL_SEC（默认 30）：
  if 不在 09:25–15:05：sleep 到下一时段（用 trade_calendar.is_open 判，非交易日直接退出）
  fetched = cpt_intraday.fetch_round_from_cpt()      # SELECT ... WHERE at = (SELECT max(at) ...)
  if fetched is None: continue                       # 表不在/读不到 → 本轮跳过，不报错
  round_at, records = fetched
  d, now = 北京(round_at).date(), 北京(round_at).time()
  prev_days = 昨日 derived_bar.cont_days（缺行 → None）
  rows = intraday_watch.scan_round(records, d=d, now=now, prev_days=..., names=...)
  loader.insert_triggers(rows)                       # ON CONFLICT DO NOTHING，首次触发为准
```

要点：
- **只认「最新一轮」**，按 `at` 分组（契约 §3 第 3 条）。不做增量游标——晚到的轮次由下一轮自然覆盖。
- 触发判据仍是 `intraday.seal_hit`（在涨停价 + 昨日非板 + 10:00 前 + 封单 ≥30 万手），
  原料换成 CPT 的 `price/prev_close/is_st/limit_price/bid1_lots`（`bid1_lots` ×100 转股）。
- `prev_days` 缺行 → `None` → `seal_hit` 判 False：**不知道昨天是不是板，就不能说今天是首板**。
- 本仓自采（`data/providers/sina_quote.py`）保留为兜底：CPT 停摆时可临时切回，但需另开采集器单元。

## D5 触发与松动（`algorithms/intraday.py` 纯函数）

#### ② 的可观测化（2026-10-22 本仓落地）

原口径「unit/cron 的 `Result=success` 且无 `failed`」有两个洞，实测都踩到了：

1. **不可观测** —— 只能人肉翻 `/home/ubuntu/logs/intraday-collect.log` 数「哪天没有 error」，

2. **"无失败"太松** —— 采集器每轮都 `skipped`（交易日判据用错表）时，同样「一条 error 都没有」，
   但其实一天都没采到东西。**2026-10-22 实测就是这个坑**：CPT 第一版
   `trading_day()` 读 `max(date) FROM public.daily_bar` 判「今天是不是交易日」，
   而 emotion-core 的日线是**盘后 17:20** 才写的 ⇒ 盘中 `daily_bar.max(date)` 恒为昨天
   ⇒ 每一轮都 `skipped`。日志里 `outcome:"skipped"` 混在 `ok` 里，一度看起来「连续 5 天无失败」，
   实则当天只采到 2 轮真数据。

   另修 timer `OnCalendar` 步长误写为小时步长、只覆盖北京 09:30–09:58 与 13:00–13:58 的问题）。

⇒ 条件 ② 的口径改成：**按「交易日 × 轮次」判定**。

- 交易日以 `public.trade_calendar.is_open` 为准（**不看 `daily_bar`** —— 同上，盘中看它必然以为今天休市）。
- 一个交易日**干净** = 当日 `outcome=error` 轮数 = 0 **且** `outcome=ok` 轮数 ≥ 10。
  - `empty` 不算失败（CPT 侧口径：没票接近涨停是正常结果）；
  - `skipped` 计入「没采到」（落不到 ok 轮数上），但**不单独惩罚**；
  - `ok` 轮数下限 10 是宽松阈值：完整时段约 150 轮，取 10 只防「整天被 skipped」。
- 连续 = 从**最近一个已完成的交易日**往回数；今天盘中未收盘（<15:00）不计入连续串，单独标 pending。

## E1 为什么是 CPT 采

C5 原来写「CPT 已有自己的盘中能力（`cpt_track/advice`）」—— 这句话是错的，实测：

| CPT 有盘口数据 | 全库表名扫 `%minute%` / `%intraday%` / `%quote%` / `%tick%`：**零** |
| CPT 能做涨停判据 | ✅ 有：`limit_up_price_cents`（禁 `*1.1`）、`derived_bar.cont_days`、`is_limit_up` / `is_bomb` |

⇒ CPT 缺的**只有采五档这一层**，口径全在那边。本仓自采要把上表 ✅ 的全部重做一遍，
且只能在另一个地方再存一份日线 —— 这正是 C5 想避免的重复建设。

## E2 分工边界

| 层 | 归谁 | 理由 |
|---|---|---|
| 原始采集（涨幅榜 / 批量五档 → 落库） | **CPT** | 口径（涨停价、板数、封住/炸板）全在 CPT，重复实现必产两套数 |

**同一个 Postgres 库** ⇒ 消费方式可以是直连查表，不必先加一层 HTTP API。

CPT 改表就是本仓瘫痪（CPT 的 `cpt_structure_event` 刚因为一次口径迁移产生过
664 行孤儿数据）。provider 换实现比换 SQL 便宜。

## E3 CPT 侧已完成（2026-10-21，CPT 仓 commit `046bc3361`）

CPT 补齐了**零副作用的那一半**：`cpt/adapters/a_share_public.py::SinaQuoteClient.fetch_quotes`。

```python
from cpt.adapters.a_share_public import SinaQuoteClient

quotes = SinaQuoteClient(timeout=10).fetch_quotes(["600519", "000002", "600519.SH"])
# -> {"600519": {...}, "000002": {...}}     键是 6 位纯代码
q = quotes["600519"]
q["last"], q["prev_close"], q["date"], q["time"]
q["bids"]   # [{"price": 1309.59, "volume": 200.0}, ... 五档]
q["asks"]   # [{"price": 1309.69, "volume": 4568.0}, ... 五档]
q["bid1_price"], q["bid1_vol"]   # 十档各有一个扁平键
```

四条契约（本仓对接时必须遵守）：

1. **键是 6 位纯代码**（`000002`），不是 `sz000002`。quote 内部仍保留全限定 `"code"`。
2. **缺档位是 `None` 不是 `0`**。停牌时新浪把价量一起填 0 → 整档 `None`。
   量本身是 0 会保留 `0.0` —— 两者含义不同，封单量判据要按 `> 阈值` 比，
   但**记录**时必须能区分。
3. **超过 50 只自动切块**（`SINA_BATCH_LIMIT`），块间各自发请求；120 只 = 3 次 HTTP。
4. **任何一段失败都抛 `ASharePublicError`，不返回部分结果**。批量采样本就要么
   全拿到要么报警 —— 静默返回一半会让「今天没触发」和「今天没采到」变成同一件事。

真实形态（CPT 实测 120 只）：停牌 `000016` 十档全 `None`；涨停 `000518` 买五档齐全、
**卖五档全空** —— 正是 D5 判据要的「封死」形态。五档齐全 118/120。

# H 实际交付变了（2026-10-22 晚，CPT R90）：`intraday_quote` → `intraday_seal_snapshot`

## H.1 变化一句话

CPT 交付的**不是原始五档流水**，是**每一轮的封板判定结论**：

| | §G 原方案 `intraday_quote` | 实际交付 `intraday_seal_snapshot` |
|---|---|---|
| 谁判涨停 | 本仓（`limit_price` / `is_at_limit`） | **CPT**（`cpt/domain/intraday_rules.seal_strength`） |
| 存的粒度 | 每轮每只票的原始五档 | 每轮每只票的**结论**（sealed / 封单量 / 涨停价） |
| 行数量级 | 40 只 × 120 轮 × 5 档明细 | 40 只 × 120 轮 = 4,800 行/日 |

理由：判据口径只能有一处。CPT 已经在算，本仓再算一遍就是两套口径，
§F.2 那个北交所 ST 的 40 条不一致就是前车之鉴。

## H.2 表结构（生产已建，实测）

```

    at          timestamptz      NOT NULL,   -- 这一轮采集时刻（UTC 存储）
    code        text             NOT NULL,   -- 6 位纯代码，与 fetch_quotes 的键同形
    sealed      boolean          NOT NULL,   -- 这一轮是否封在板上
    bid1_lots   double precision,            -- 封单量（手），判不了为 NULL
    limit_price double precision,            -- 本轮用的涨停价（存下来自证口径）
    PRIMARY KEY (at, code)
)
-- 索引：idx_intraday_seal_snapshot_code_at (code, at)
--       idx_intraday_seal_snapshot_at (at DESC)
```

本仓用 `connect_ro()` 实测可见：5 列类型如上，2026-10-22 首批 99 行 / 3 轮。

## H.3 三条读表口径（错了会造出并不存在的状态）

1. **没行 = 判不了**，不是「没封板」。候选之外、停牌、缺档位的票不会有行。
2. **`sealed=False`** 是「采到了、这一轮没封在板上」—— 这是「开板」的证据。
3. **按 `at` 分组取最新一轮**，不要按 `code` 单点查最新。跨轮混算会把
   「上一轮封着、这一轮开板」读成两只票。

本仓要的「今天哪只封了、封了多久、开没开板」，用
`SELECT at, code, sealed, bid1_lots FROM intraday_seal_snapshot
 WHERE at >= %s AND at < %s ORDER BY at, code` 拿一天的行，在内存里按 code 分组即可
（CPT 侧 `cpt/application/intraday_review.py` 就是这么算的，可直接对照）。

## H.9 切换常驻：卡死告警 + 收盘自动结算（2026-10-23 下午）

**起因**：奎爷问「不是有常驻进程吗？这两条 cron 都不需要了吧」。答案是「能替代，但缺一块」——
`--loop` 里 `fetch_rounds` 读不到时只 `log.warning("CPT 表不存在或读不到，本轮跳过")`，
不进日志聚合、不推送。CPT 采集挂了，本进程会安安静静待一整天，台账不长也没人知道。
两条 cron 恰恰是在补这块。所以切换前先把缺口补上。

1. **卡死告警**（`services/intraday_watch.py`）
   - `STALE_MINUTES = 8`（CPT 每 2 分钟落一轮，留 4 轮余量）、`ALARM_GAP_SEC = 1800`（同类告警半小时内不重复，免得 CPT 挂一上午刷一百条）。
   - `_round_age_min(round_at, now)`：`round_at` 是 UTC `datetime` → 换算北京时间再算分钟差；`round_at` 缺失（表不存在 / 读失败）也算「不新鲜」，走另一段文案。
   - 文案说清三件事：现在几点、数据停在哪一轮（已 X 分钟）、去哪里查（`systemctl status cpt-intraday-collect.timer` + `tail ~/logs/intraday-collect.log`）。
2. **收盘自动结算**：`SETTLE_AFTER = 15:05`，非盘中且当天未结过 → 跑一次 `settle(今天)` 并推汇总（触发 N / 结算 M / 待定 K）。没有这条，台账会永远停在 `settled_at IS NULL`。
3. **日志降噪**：`run_round(quiet=)` —— 同一轮次重复读（30 秒一轮 × CPT 2 分钟一轮 = 4 次）且没写入时降到 DEBUG。改之前服务日志一天两千多条一模一样。
4. **推送通道**：`services/notify.py` 新增公开 `push_text(text)`，不走 LLM 改写。告警与结算摘要都是机器事实，改写只会增加失真风险；`push()` 那条是给日报摘要用的。
5. **切换**：`systemctl enable --now emotion-intraday.service` → `enabled` / `active`；随后删掉两条盘中 cron（上午场 / 下午场）。判据、报警、结算此后都由常驻进程负责。

**验证**：tests/unit/test_intraday_watch.py 新增 `TestRoundAge`(3) / `TestLoopAlarm`(4，含节流与「读不到」文案) / `TestLoopSettle`(3，含「没触发不推」「收盘前不结」)；全量 3107 例通过。当日实跑日志 `round … 21 票 → 确认轮数 2 → 触发 0 条 → 写入 0 条`（早盘 10:00 截止已过，下午不产触发是设计）。

### H.9.1 上线当天就撞到的两个假警（2026-10-23 12:00–12:15 实测后修）

启用后十分钟内发现两处会天天误报的地方，都是「本仓假设 CPT 全天连续采集」造成的：

1. **午休假警**。CPT 的 timer 是 `09..11,13..14:00/2:00` —— **11:30–13:00 午休本来就不落轮次**；本进程场次写成连续 `09:25–15:05`，于是午休里「最新一轮」必然越来越旧，`STALE_MINUTES=8` 到点就报。每天三条假警，正好把真事故淹掉。
   修法：`SESSION_WINDOWS = ((09:25, 11:32), (12:58, 15:05))` —— 按 CPT 的采集窗口切两段，午休不扫表也不判新鲜度；上午多留 2 分钟、下午提前 2 分钟是给最后一轮/第一轮留落库余量。`in_session()` 改为「落在任一窗口内」。
2. **开盘前假警**。09:25 进场时 CPT 还没采（09:30 起采、约 09:32 落首轮），「没有轮次」是正常的。
   修法：`ALARM_GRACE_UNTIL = 09:35`，在此之前只扫不报。
3. **顺带补的可观测性**：告警原来成功时不留任何日志，事后无法回溯「今天到底报没报过」。现在 `log.warning("卡死告警已触发（已推送 / 推送未配置…）：最新一轮 X，距今 N 分钟")`。

**验证**：场次边界实测 09:24 False / 09:25 True / 11:31 True / 11:33 False / 12:00 False / 12:57 False / 12:58 True / 15:05 True / 15:06 False；新增 `TestSession::test_lunch_break_is_out_of_session` 与 `TestAlarmGrace`(3)；tests/unit/test_intraday_watch.py 60 passed。

### H.9.2 结算跑错了时间窗，也结错了日期（2026-10-23 15:05 实跑暴露）

15:05 自动结算确实跑了，日志是「触发 5 条，结算 0 条，待定 5 条」。待定本身不算异常，但这个实现里有两个真 bug：

1. **结得太早**。D 日盘中触发的卖出价是 **D+1 的开盘**，而 D+1 的日线要等 D+1 盘后 pipeline（17:20）才落库。15:05 去结，D+1 的数据必然还不存在 → 永远「待定」。
2. **只结「今天」，昨天那批永久漏掉**。`loop` 里写的是 `settle(now.date())`：10-23 的 5 条触发，到 10-26 那天只会去结 10-26 自己的触发，10-23 这批没有任何一次「结今天」会碰到它 → 永远停在 `settled_at IS NULL`。

修法：

- `SETTLE_AFTER = 17:35`（盘后 pipeline 之后）。
- 新增 `loader.pending_trigger_dates(before)`（`SELECT DISTINCT date FROM trigger_log WHERE settled_at IS NULL AND date < %s`）与 `services/intraday_watch.settle_pending(as_of=)`，一次把所有欠账日期按升序结掉。
- `loop` 的收盘分支改调 `settle_pending`，日志与推送按「N 天欠账 / 触发 X / 结算 Y / 待定 Z」汇总。

**验证**：`pending_trigger_dates(date.today())` → `[]`（今天没有更早欠账）；模拟 `settle_pending(as_of=2026-10-26, dry_run=True)` → `[('2026-10-23', 5, 0, 5)]`（周一 10-26 才会拿到卖出价，符合预期）；新增 `TestSettlePending`(2) 与改写 `TestLoopSettle`(3，含「同一天只结一次」「17:00 不结」)；`test_intraday_watch.py` 62 passed。
